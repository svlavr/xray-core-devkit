# Checkout configuration and startup

The installer copies maintained policy and tooling. `workspace.py setup`
generates a host layer for one explicitly selected Xray Git checkout; it does
not change global Codex configuration, authentication, remotes or Git settings.
Run setup from that installed source root, as in
[installation](INSTALLATION.md#3-generate-and-verify-checkout-settings).

## Editable inputs and generated state

Edit the maintained source of a setting, then regenerate and start fresh
processes. The [file map](FILES.md) lists every component; the main inputs are:

- `.codex/agents/*.toml`: eleven role models, effort, role intent and task rules.
- `.agents/orchestration/context.json`: nominal context window, effective
  percentage, compaction percentage, scope and required model family.
- `.agents/scripts/language_policy.py`: shared primary/worker language text.
- `.agents/scripts/workspace.py`: generated feature flags, native capacity,
  MCP entries and checkout verification.
- `.agents/dependencies/analysis-lock.json` and adjacent npm locks: analysis
  dependency versions. Changing them requires provisioning the new dependency
  set; setup alone does not install tools.
- `.agents/orchestration/models.json`, `.agents/runtime-lock.json` and
  `.agents/orchestration/city.toml`: external routing/runtime defaults. External
  host selection is separate; see [orchestration](ORCHESTRATION.md).
- Optional owner-created `.agents/project.json`: branch/baseline and repository
  publication policy, described below.

These tracked toolkit files are update-managed. Local customization is allowed,
but later updates preserve it and report a conflict for explicit reconciliation.
A change to models, context or role policy also needs matching validation rules
and capability evidence; it is not a supported arbitrary config override.

Setup writes two ignored, untracked host files:

- `.local/workspace/context.json`: canonical source root, selected branch and
  baseline, observed fetch/push URLs, Python/Git/Node paths, analysis-tools root
  and generated-config digest.
- `.codex/config.toml`: generated context, language, role and MCP configuration.

Setup replaces each complete generated file atomically. Temporary files stay
under ignored `.local/workspace/`; a short-lived recovery digest in the context
allows setup to finish an interrupted context/config update. It is removed after
successful completion. This recovery accepts exact known generated bytes only.

The installer also records copied-file hashes in
`.local/workspace/devkit-install.json`. Prepared external workers use
`.local/workspace/worker.json`; that marker carries their own exact root/base and
queue, not main's publication authority. Owned disposable scratch is under
`.local/host/transient/`. Keep durable evidence outside scratch. Authentication
comes from the user's own account state and is never copied by this toolkit.

## Branch and baseline selection

Setup requires the exact `github.com/xtls/xray-core` module, a named branch and a
local initial commit. It records the current branch and rejects detached HEAD.
By default, each setup selects current HEAD as a **comparison** baseline. For
another local ancestor, pass its full 40-character SHA:

```powershell
python .agents/scripts/workspace.py setup --analysis-tools D:/Tools/xray-analysis --baseline <full-40-character-SHA>
```

Replace the placeholder before running the command. Setup does not fetch,
resolve a remote branch or establish an officially adopted upstream revision.
The owner supplies that evidence separately. Verification retains the saved
branch/baseline until setup is rerun; changing branch requires a new setup.
A configured `expected_branch` must agree with the selected branch.

The user may create `.agents/project.json` with nonempty string values. Supported
keys are `baseline`, `expected_branch`, `integrating_url`, `integrating_branch`,
`public_url`, `public_branch`, `anchor` and `public_push_mode`. A baseline-only
example is:

```json
{
  "baseline": "<full-40-character-local-ancestor-SHA>"
}
```

Use an actual SHA, not the example placeholder. An explicit setup `--baseline`
takes precedence over this file. Without either, setup selects current HEAD even
when old ignored context contains a previous baseline. Verification uses saved
branch/baseline values, so editing project defaults takes effect through setup.

Destination fields express optional owner policy; they do not change remotes or
authorize a task. No fork URL, private branch or private contract is supplied.
Filtered export additionally requires an owner-provided
`.agents/public-export.json` and explicit destination authority. Only explicit
`public_push_mode: "filtered-export-only"` can allow the exporter's publication
guard. See [accounting and export](ACCOUNTING_AND_EXPORT.md).

## Existing local configuration

Both generated host paths and `.local/workspace/.setup-probe.tmp` must already
be ignored and untracked. The probe checks the temporary-file location; ignoring
only `context.json` is insufficient. Installation adds ignore rules to
`.gitignore`; setup checks existing rules without editing
`.git/info/exclude`, including in linked worktrees. It preserves source/index
changes. Host files cannot be symlinks, hardlink aliases or below reparse-point
directories.

If `.codex/config.toml` already exists without toolkit context, setup stops and
preserves it. If a generated config was manually edited, regeneration also
stops. Save a copy of that exact file in your own local location, review which
settings you need, then move the edited config aside before rerunning setup.
Keep needed customization in its maintained source or separate user settings;
setup does not merge arbitrary config. Do not remove the install receipt or
track host state to bypass these guards.

If setup was interrupted during a generated update, rerun the same setup command
with the intended tools root and baseline. Its saved recovery digest allows the
known prior/new generated files to be reconciled without treating the interruption
as a manual edit. Do not move files aside merely for this retry. An actual
manual-edit error still requires preserving and reviewing those edits.

After a deliberate policy/tool-path update, run from the source root:

```powershell
python .agents/scripts/workspace.py setup --analysis-tools D:/Tools/xray-analysis
```

```powershell
python .agents/scripts/workspace.py verify
```

```powershell
python .agents/scripts/session.py --
```

Pass the selected baseline again if it is not in `.agents/project.json`.
Regeneration applies new configuration; fresh sessions/processes adopt new
roles and launchers. Existing chats can retain their old configuration.

## Native agents, models and language

The generated config sets `features.multi_agent_v2 = true`, `agents.enabled =
true`, default subagent model `gpt-6.1-sol`, default subagent effort `high`,
`max_concurrent_threads_per_session = 23` and `interrupt_message = true`.
Capacity remains subject to observed session/host limits. Role paths refer to
all eleven distributed TOML files; each disables nested native workers.

Validation requires the complete managed set of thirteen skills and eleven roles.
Source-owned extra skills/roles are preserved and reported separately as
`additional_skills` and `additional_roles`. The generated layer explicitly
registers only the eleven managed roles; source-owned roles remain subject to
Codex's native discovery rather than being rewritten into the managed config.

The thirteen skills and eleven roles are retained. `mu_explorer` uses
`gpt-6-luna` high, ordinary worker/review roles use `gpt-6.1-sol` high, and
`mu_deep_reviewer` uses `gpt-6-astra` high for one evidenced unresolved question.
Main's model and effort are not overridden. Internal tasks, reports and docs use
English; direct primary-coordinator replies use Russian.

Role `sandbox_mode` is `read-only` except `mu_go_worker`, which declares
`workspace-write`. These values express task intent and do not enforce a
separate OS boundary or expand access. The parent session's effective sandbox
and approval settings govern tools. Assigned read/write limits still apply.

## Context policy and local capability checks

The maintained policy requests 872000 nominal tokens, 95% effective capacity
(828400), and compaction at 80% of that effective capacity (662720). The
corresponding generated keys are:

```toml
model_context_window = 872000
model_auto_compact_token_limit = 662720
model_auto_compact_token_limit_scope = "total"
```

The policy's required models are `gpt-6-astra`, `gpt-6.1-sol` and `gpt-6-luna`.
Verification reads `models_cache.json` under `CODEX_HOME`, or the user's `.codex`
directory when that environment variable is absent. An available catalog must
cover the required nominal capacity and effective percentage for every required
model. An incompatible catalog blocks verification. An absent catalog is
`UNKNOWN`, not a successful access check.

Choose an explicit read-only catalog and require it to exist when desired:

```powershell
python .agents/scripts/workspace.py verify --catalog D:/Local/models_cache.json --require-capabilities
```

These flags also work with `setup`. Setup does not authenticate or query online
capabilities. A compatible local catalog, generated config and successful launch
are distinct from account access and confirmed session adoption. For a specific
compaction event, use [context_diagnostics.py](../.agents/scripts/context_diagnostics.py)
with the exact thread ID; it reads bounded local accounting evidence without
printing prompts or credentials. See its `--help` and the evidence discussion
in [workflow](WORKFLOW.md).

## MCP settings

Windows gopls, GitNexus, Context7 and grep.app are enabled. Android gopls is configured but
initially disabled. Repomix is included only when its installed backend file and
a Node executable are available at generation time. Both Go profiles expose
`go_workspace`, `go_search`, `go_file_context`, `go_package_api`,
`go_symbol_references` and `go_diagnostics`. GitNexus exposes `list_repos`,
`query`, `context`, `impact`, `trace` and `check`.

Local MCP entries have a 60-second startup limit and 240-second tool limit.
Go/GitNexus entries request `default_tools_approval_mode = "auto"`; parent
permissions still govern actual access. Context7 uses
`https://mcp.context7.com/mcp` and receives public documentation queries only.
grep.app uses `https://mcp.grep.app` for public GitHub code examples, with only
`searchGitHub` enabled, automatic tool approval, and 60-second startup/tool
deadlines. Both services are configured in primary and generated external-worker
profiles. Send public queries only; never transmit private source, contracts,
credentials or logs. Review the source revision, actual caller and applicable
license before adopting a result. Service approval settings do not override
the parent session's effective permissions. Fresh sessions adopt regenerated
configuration; existing sessions may retain their prior MCP catalog.
Repomix uses the managed relay and a sandbox rooted at the selected checkout;
that root restriction is not a public-disclosure allowlist.

Setup does not run servers, build indexes or start a platform matrix.
`workspace.py verify` checks config agreement and selected executable/path
presence; it is not a backend health test. Actual MCP use must record the
selected root/profile and successful needed operation. See [analysis](ANALYSIS.md)
for opt-in profiles, build tags and graph limits.

`session.py` flattens the verified local layer into per-invocation Codex settings
and resolves role paths to absolute paths. Generation and invocation preserve
Unicode paths and paths containing spaces; quote such paths in shell commands.
The launcher leaves global/account files untouched. The CLI may still need the
user's usual project trust flow.

## Source accounting

A fresh source checkout has no fork-specific owner catalog or snapshot. Startup
reports `UNINITIALIZED` until the owner supplies `.agents/metrics/modules.json`
and `.agents/metrics/source-size.json` through the
[source-accounting workflow](ACCOUNTING_AND_EXPORT.md). Optional shared ownership
uses `.agents/metrics/shared-integration.json`.

Uninitialized accounting is explicit missing evidence and permits ordinary
toolkit startup. An initialized invalid/stale catalog or snapshot remains an
error. Never fabricate module totals or transfer another project's acceptance.
